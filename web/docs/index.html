Verify a domain

You cannot send from a domain until it passes SPF and DKIM. This is not us being strict — mail from an unverified domain is rejected or filtered by the receiving server, so sending it would just burn your reputation.

  1. In your dashboard, go to Domains → Add domain and enter the domain your mail comes from, e.g. yourshop.com.
  2. We generate a DKIM keypair and show you the exact records to publish.
  3. Add them at your DNS provider. SPF and DKIM are required; DMARC and the return path are recommended.
  4. Press Recheck. We also re-check every two minutes on our own.
This does not touch your MX records. Your inbox — Google Workspace, Microsoft 365, whatever you use — keeps working exactly as it does now.

Typical records

TypeNamePurpose
TXTyourshop.comSPF — authorises our IPs to send as you
TXTpostal._domainkey.yourshop.comDKIM — the public key for our signature
TXT_dmarc.yourshop.comDMARC — tells receivers what to do with failures
CNAMEpsrp.yourshop.comReturn path — where bounces are collected
Already have an SPF record? You may only have one. Merge ours into it rather than adding a second — two SPF records is a permanent error, and receivers will treat every message as unauthenticated.

Send via SMTP

Anything that already sends email can point at us with no code changes.

Hostsmtp.mailkong.net
Port587
SecuritySTARTTLS
UsernameFrom Credentials → New SMTP user
PasswordShown once when you create it
Use port 587, not 25. Port 25 is for server-to-server delivery and is blocked outbound by most networks and hosting providers. 
# Nodemailer
const transport = nodemailer.createTransport({
  host: 'smtp.mailkong.net',
  port: 587,
  secure: false,        // STARTTLS is negotiated after connecting
  auth: { user: process.env.SMTP_USER, pass: process.env.SMTP_PASS },
})

Send via the HTTP API

Create an API key under Credentials. It is shown once.

curl https://api.mailkong.net/v1/messages \
  -H "Authorization: Bearer pk_live_..." \
  -H "Content-Type: application/json" \
  -d '{
    "from": "Billing <billing@yourshop.com>",
    "to": ["customer@example.org"],
    "subject": "Your receipt",
    "html": "<p>Thanks for your order.</p>",
    "text": "Thanks for your order.",
    "tag": "receipt",
    "metadata": { "order_id": "4821" }
  }'
{ "id": "cm4x9k2p0000abcd", "status": "queued", "suppressed": [] }

Always send text alongside html. A message with no plain-text part is a well-known spam signal, and it is the single cheapest thing you can do for deliverability.

Tags and metadata

tag is a label you filter Activity by — receipt, password-reset. metadata is an arbitrary object returned unchanged on the message and on every webhook about it, which is how you tie a delivery event back to your own records without a lookup table.

Suppressed recipients

Recipients on your suppression list are dropped rather than failing the whole call, and returned in suppressed. If every recipient is suppressed, the call fails with all_recipients_suppressed.

Verifying a delivery

Every request carries X-Mail-Timestamp and X-Mail-Signature. The signature is HMAC-SHA256(secret, "<timestamp>.<raw body>"), hex encoded. 

import crypto from 'node:crypto'

app.post('/hooks/mail', express.raw({ type: 'application/json' }), (req, res) => {
  const timestamp = req.headers['x-mail-timestamp']
  const signature = req.headers['x-mail-signature']

  // Reject anything older than five minutes so a captured payload
  // cannot be replayed indefinitely.
  if (Math.abs(Date.now() / 1000 - Number(timestamp)) > 300) {
    return res.sendStatus(400)
  }

  const expected = crypto
    .createHmac('sha256', process.env.MAILKONG_WEBHOOK_SECRET)
    .update(`${timestamp}.${req.body}`)
    .digest('hex')

  if (!crypto.timingSafeEqual(Buffer.from(expected), Buffer.from(signature))) {
    return res.sendStatus(401)
  }

  const event = JSON.parse(req.body)
  res.sendStatus(200)          // respond fast; do the work afterwards
})
Sign the raw body, before any JSON parsing. Parsing and re-serialising changes the bytes and the signature will never match.

Retries

Any non-2xx response is retried five times with exponential backoff, over roughly ten minutes. After 50 consecutive failures the endpoint is disabled and you are emailed. Respond 200 as soon as you have the payload and process it asynchronously.

Inbound routes

Turn replies into webhooks instead of a mailbox nobody reads.

  1. Add an MX record: inbound.yourshop.com → routes.mailkong.net, priority 10.
  2. Create a route under Inbound: an address (support, or * for a catch-all), the domain, and your endpoint URL.

Mail arriving there is parsed and POSTed as JSON, signed exactly like any other webhook:

{
  "event": "inbound.message",
  "data": {
    "from": "customer@example.org",
    "to": "support@inbound.yourshop.com",
    "subject": "Re: Your receipt",
    "text": "Can I change the shipping address?",
    "html": "<p>Can I change the shipping address?</p>",
    "headers": { "message-id": "..." },
    "attachments": [],
    "spam_score": 0.4
  }
}

Suppressions

Hard bounces and spam complaints are added to your suppression list automatically and blocked on the next send. This is not optional and it is not configurable — repeatedly mailing addresses that have already rejected you is the fastest way to get an entire sending pool blocked.

You can add addresses manually, remove ones you believe are wrong, and export the list as CSV. Platform-wide suppressions are marked as such and cannot be removed from your account; contact support if you think one is a mistake.

Error format

Branch on code, never on message — messages are written for humans and will change. 

{
  "error": {
    "code": "domain_not_verified",
    "message": "yourshop.com has not passed SPF and DKIM checks yet.",
    "detail": { "spf": true, "dkim": false, "dmarc": false }
  }
}
StatusMeaning
401Missing or invalid API key
402A plan or quota condition — reserved for this, so you can distinguish it from a permissions problem
403Account paused, disabled, or awaiting domain verification
422The request body failed validation; detail lists the fields
429Rate limited — back off and retry
500Our fault. request_id is what support needs.
